## 1. 用户已明确的目标与范围

使用 Python 构建面向普通人的综合法律问题处理助手，逐步覆盖中国大陆刑事、民事、行政、劳动及程序性资料。用户描述事情后，系统应理解事实、必要时追问、检索法律与案例、说明处理路径和证据要求、提供可核对出处及不确定性。成熟后计划开源。

范围采用“综合法律目录 + 分领域验证”双轨：

- 目录、来源与数据规范从第一版起就按跨领域建设，不能因劳动试点阻止刑事、民事、行政资料进入统一目录。
- 劳动是首个试点/深样领域，不是唯一领域；首批验证劳动（可加刑事、民事抽样），行政可先建目录。
- 首期不宣称综合法律能力；目录已建、样本已入库、Schema 已交付，都不等于领域问答可靠。
- 历史版本必须保留：已失效但适用于案件发生/行为时的文本不得因“当前失效”被排除；系统按案件时间、持续状态与过渡规定选择适用版本。

用户希望系统学习类似律师的分析和办事方式，不只是背诵法条。此目标不等于系统获得执业律师资格或具备替代专业法律服务的可靠性。

## 2. 对外部建议的采纳与纠正

### 2.1 采纳

- 案例结构化、法律与案例联合检索、比对类案事实差异、先建资料底座与测试再决定微调。
- 案例原文优先，结构化要点必须可定位回原文。
- 主张、认定、理由、官方要旨、模型总结分字段保存。
- 案例身份多标签，不排成互斥的单一效力等级。
- 先评测原模型 + RAG，再决定是否微调。

### 2.2 纠正

- 结构化摘要不能替代原文。采用“原始资料 + 可定位的结构化要点 + 检索索引”，允许按字段和全文联合检索；是否优于其他方案要实测。
- 分开记录当事人主张、法院认定事实、裁判理由和模型提取内容；不得把“被告辩称”抽成法院认定事实。原文未写明的字段允许缺失，不让模型强行补全。
- “法条定性质、案例定尺度”仅是简化说法。法律、司法解释、程序规则与个案事实共同影响分析，案例不是裁判结果预测器。
- 指导性、入库参考、公报、典型等身份可能重叠，不建成互斥的单一“效力等级”枚举；但身份的规范依据与效果要分别记录。
- 不能按旧案例金额或结果直接计算用户案件金额、胜诉率或必经程序。
- 不承诺一次下载“所有法律”。需要可审计目录、范围声明、缺口记录和持续更新机制。

### 2.3 本轮审查后的修正

- 案例库是类案参考的官方主渠道；不因“只收入库案例”否定其类案检索作用。检索覆盖应在回答中声明为“入库/已发布案例”，不宣称全量类案。
- 法律冲突不能靠“上位法/特别法/新法”简单排序自动解决。系统只做失效/未生效/版本时间等事实过滤；对特别法/新法、上位法关系只提示，冲突标“待核实/待裁决”，不自动选择、不自行裁决。
- 样本数量不自动等于验证充分。首批保持小规模，按覆盖矩阵组织；数量只作预算，不写成领域可靠性验收门槛。
- 隐私排除不得直接写成法律禁令。按“法律限制/官方公开状态/再利用许可/项目采集政策”四层分别核查。

## 3. 覆盖范围与领域状态

### 3.1 领域目录

至少区分：宪法及国家机构相关、刑事、民商事、行政及行政救济、劳动与社会保障、诉讼/仲裁/执行/证据程序。领域标签允许交叉，不将所有材料强行归为唯一类别。

刑事覆盖不仅包括刑法，还应考虑修正及版本关系、刑事诉讼、相关解释和程序性权利信息；民商事需关联诉讼、证据与执行资料；行政需关联行政复议、行政诉讼与赔偿；劳动需关联仲裁、工伤与社会保障。具体规则清单由来源核验和审查决定，本稿不宣称清单穷尽。

### 3.2 资料类型、位阶与依据资格

资料类型至少区分（可按首批需要先收常见类型）：

- 宪法；
- 法律；
- 行政法规；
- 地方性法规；
- 自治条例和单行条例；
- 经济特区法规；
- 部门规章；
- 地方政府规章；
- 司法解释；
- 司法解释性质文件及其他规范性文件（会议纪要、答复、指导意见等）；
- 军事法规规章、国际条约（按目标场景再启用）。

类型不等于依据资格。能否作为“本案处置法定依据”取决于文件性质、制定权限和适用条件：

- 裁判依据：法律、行政法规、地方性法规等（具体以程序法/实体法规定为准）；
- 参照：规章在行政诉讼中参照；
- 说理参考：其他规范性文件、会议纪要/答复、案例等，不得单独作为裁判依据；
- 程序指引：流程性材料，不能支撑实体结论。

同一事项存在冲突时，系统只做失效/未生效/版本时间等事实过滤；特别法/新法、上位法关系只生成提示；冲突一律标“待核实/待裁决”，并列展示可能文本，不自动选择。

### 3.3 领域状态与历史版本

每个领域分别报告：目录已登记、原文已取得、内容已核验、索引可检索、问答已评测。不得以“资料入库”冒充“专业能力验收通过”。

历史版本作为独立版本保留，与现行版本建立关系；不默认排除废止文本。适用版本按案件发生/行为时、持续状态、过渡规定与例外选择，不能只按“当前是否有效”过滤。案例的裁判时适用法律版本也要记录，用于类案可比性判断。

## 4. 数据规范

### 4.1 法律资料

字段需求：稳定资料 ID、版本 ID、标题、资料类型、制定机关、发布机关、文号、领域标签、适用地域、公布/施行/修订/失效日期及未知状态、效力状态及核验依据、制定/授权依据、效力位阶、依据资格、版本关系、过渡规定关联、官方来源 URL、采集及核验记录、原文文件和内容摘要值、再利用依据。

条款结构：编/章/节/条/款/项/目按原文实际结构保存；无编号的款/项也要能保存；缺失层级允许为空。采用父子关联，保留完整条文和跨条引用。检索块记录所对应版本、条款和原文位置，不能把不同版本同号条文合并。

历史版本：保留旧版本全文、失效/修订日期与依据；废止日期未知允许为 null，不因此丢弃历史版本。建立新旧版本关系与条款号变更映射；案件时间适用必须检查过渡规定、例外和适用条件；无法判定时标“待核实”并降级。

### 4.2 案例资料

字段需求：稳定案例 ID、案号（缺失允许为空）、官方发布/入库编号、标题、法院、审级、审理程序、裁判类型、裁判日期、发布日期、地域、案由或罪名及其原始表达与标准化值、标准化所依据的版本、来源 URL、来源主体、原文快照/校验值。

案例身份采用多标签或关联记录，分别记录：指导性案例编号及状态、人民法院案例库入库身份和编号、公报刊载、典型案例发布批次、地方参考性案例、最高检案例、普通裁判文书身份；每项记录授予主体、文件/批次、日期、来源、核验状态（VERIFIED/UNVERIFIED/UNKNOWN）、核验时间和规范效果（“应当参照/参考/无正式参照效力”）。未核验身份只能给 UNKNOWN 规范效果，不得展示为已确认身份；不得靠模型判断自动授予权威身份。

内容分区：诉辩主张、法院认定事实、争议焦点、证据及其采信说明、程序经过、裁判理由、适用依据、裁判结果、官方裁判要旨、模型提取要点。每段关联原文定位、抽取方式、模型版本、审校状态、主体标签（原告/被告/第三人/公诉人/辩护人/法院）。不存在的信息标为未提供，不虚构。

官方要旨分来源保存：指导性案例“裁判要点”、案例库参考案例“裁判要旨”、公报案例“裁判摘要”、典型案例“典型意义”（栏目名称以官方页面实际标注为准），各自记录来源与原文定位；不得合并成一个“官方要旨”字段。模型总结可缺省或为 null，不得为满足 Schema 编造模型版本；模型总结可用于候选召回，但未经核对不能以“法院认为”或官方裁判规则展示。

裁判生效情况、再审/改判/撤销或案例不再参照情况：记录已知状态、依据和核验时间；无法确认时标未知。相同案件的不同审级文书、串案与关联案件应建立关联，不能简单视为多个独立同向案例。

适用法律版本：记录案例裁判时所依据的法规 ID、版本 ID、条号，供类案可比性与版本冲突判断。

公开与采集状态：分别记录案件是否公开审理、裁判文书是否公开上网、案例是否官方发布、是否已隐名，以及项目采集政策；四者不得互相替代。

### 4.3 Schema 交付要求

机器可读 Schema v0 位于 `schema/`：

- `legal_document.schema.json`：法规/司法解释文档与条款结构；
- `case_document.schema.json`：案例文档、身份、分区、引用卡片；
- `README.md`：字段说明、首批必填子集、正反样例、校验方法与版本兼容策略；
- `examples/`：有效/无效样例，覆盖缺失、未知、冲突、多身份重叠、历史版本。

实现前明确必填/可空/缺失含义、日期格式、枚举、列表、跨字段校验和版本兼容；不将本节字段清单直接宣称为完成的机器契约。首批可只要求一个最小必填子集，其余字段允许为空。

## 5. 来源目录、获取与更新

### 5.1 候选来源

首批来源目录见 `source_catalog_v1.md`，至少包含：

- 国家法律法规数据库（`flk.npc.gov.cn`）；
- 全国人大网、中国政府网、司法部/国家规章库（法规原文候选）；
- 最高人民法院官网（`court.gov.cn`）；
- 人民法院案例库（`rmfyalk.court.gov.cn`，类案参考主来源）；
- 最高人民法院公报（公报案例）；
- 最高人民检察院官网（指导性案例、典型案例、检察解释）；
- 裁判文书网（普通裁判文书，可选扩展，获取限制未知）；
- 地方人大/政府法规规章入口（按领域需要）。

### 5.2 来源字段与未知标记

来源目录须包含：入口名称/URL、覆盖类型和领域、权威身份依据、权威分级（官方原文/官方转载/商业汇编）、获取方式、是否需登录、是否可批量、自动采集限制、再利用说明、最近核验时间、可访问状态、更新方式与已知缺口。

**来源实际无法核验时标记“未知”，不推断登录、API、批量导出或许可条件。**“未知”不是“可用”，也不是“不可用”；在核验前不得据此承诺功能，也不得把商业转载冒充官方原文。

官方可查不等于有公开批量下载 API，不等于可绕过登录、验证码或访问控制；不在本稿虚构接口。资料获取可从允许的导出、手动保存或有明确许可的方式开始，批量采集另行验证。不复制商业数据库的解读或编辑内容作为默认开放数据。

### 5.3 获取、更新与缺口

更新要求：保留抓取快照及变更记录；修订不覆盖旧版本；来源消失、内容变化、案例改判或身份变化须标记并影响引用提示。更新周期按来源确定；展示最后核验时间，过期或未核验不显示“实时有效”。

案例检索覆盖应在输出中声明：本次覆盖的是入库/已发布案例，普通文书是否在覆盖范围内。未检索到案例不等于没有类似案例。

## 6. 联合检索与回答流程

1. 识别问题领域、诉求、地域、事件时间及紧急风险；缺少关键事实时追问。
2. 法律检索可采用关键词、向量与元数据过滤；先按依据资格、效力状态与版本过滤，再按相关性排序。版本不明或存在冲突时展示候选与缺口，不擅自选定适用版本，不自动裁决冲突。
3. 案例检索按事实、争议焦点、程序与裁判理由召回，结合身份、地域、日期、法律版本及审级筛选；关键词/向量/重排均是待实测方案。默认同时检索支持与不支持/不同方向的案例。
4. 输出相似与不同之处、参考价值与限制、可能影响处理路径的关键证据；必要时说明存在不同方向案例，避免只检索支持既定观点的案例。
5. 结论分别链接法条依据和案例说理参考，不能用案例摘要替代法律依据；法条与案例分别标注“法定依据/类案参考/背景资料”。所有引用回到可核对原文。
6. 回答固定“覆盖声明”：本次检索覆盖哪些来源/领域/版本；未覆盖什么；案例检索是否仅覆盖入库案例。

检索未命中不等于法律不存在或没有类似案件。资料不可用、文本核验失败、版本不确定、领域未验证或事实不足时，按现有 PRD 降级，禁止生成虚假出处。未建立期限/程序规则的领域不得输出确定期限或确定程序。

## 7. RAG 与微调的分工

法律/案例原文先进入知识库，检索向量用于召回，不直接作为聊天模型 SFT 输入。

微调候选数据形式：经审查的案情及多轮对话、给定法条/案例上下文、目标回答，覆盖必要追问、条件分析、引用、事实差异、范围外问题和承认缺口。标签必须区分官方信息、用户陈述和推断。

先评测原模型加 RAG，再根据错误类型决定是否微调；检索或版本错误不能靠微调掩盖。微调也可能学习领域知识与任务能力，但不能保证记住最新法律、消除幻觉或获得律师资质。

训练/调试/留出评测按案件及近重复族隔离，避免同案不同文书或改写题跨集合造成泄漏；同时按时间（法规版本变化）与领域切分。自动生成训练答案必须经过核对，不直接作为正确标签；真实咨询不默认上传云端。训练上下文应由同一检索管线采样，包含检索失败/噪声/不完整样本，避免训练用干净法条、推理用脏检索。

当前 Colab 仅完成：T4 可用、PyTorch 识别 CUDA、Qwen3-8B 4-bit 加载及一次无 RAG 回答。截图显示加载后已分配显存约 5.67GiB；尚无训练成功或法律效果达标证据。免费训练是否完成需实测。案例与法规保存不能依赖临时运行时。

## 8. 第一批交付与验收

本批只要求“管线与契约”验证，不验证领域可靠性，不宣布任何领域问答达标。首批交付应包含：

- 跨领域来源目录 v1 及缺口清单，覆盖刑事、民事、行政、劳动和程序资料，不限定为劳动资料目录；
- 法规及案例机器 Schema v0、字段说明、首批必填子集、有效/无效样例和校验方法；
- 小规模首批样本：按覆盖矩阵组织，而不是按“每领域若干部/个”的硬数量。覆盖维度至少包括：
  - 同一部法规新旧版本（或旧版被修正的条款）；
  - 同一案件不同审级或二审改判/再审关联；
  - 主体相似但关键事实不同、结论不同的案例；
  - 检索未命中、引用不支持结论、版本串用各 1 例；
  - 指导性案例、案例库参考案例、公报/典型案例、普通文书各至少 1 个；
  - “被告辩称”与“法院认定”相邻且易混的段落；
  - 每个纳入验证的领域至少 1 条完整链路。
- 法规 5～8 部、案例 6～10 个可作为预算起点，但数量不是验收门槛；最终由覆盖矩阵和可获取性决定。
- 可重复导入及检索验证：原文、分区、来源、版本和索引可追踪，先验证基本检索再比较向量与混合方案。
- 每个样板领域提供基本检索题，并含反例（相似事实不同结果、旧版本、主张/认定混淆、二审改判、无结果、引用不支持结论）。
- 检查 Schema 有效、原文可定位、模型摘要可区分、不同版本不串用、历史版本可检索、类案差异能展示、身份标注正确、未知信息不补造。报告样本覆盖与失败项，不能仅用演示题宣布领域可靠。

## 9. 安全、隐私与开源边界

继承现有 PRD：`LOCAL_ONLY` 限制覆盖生成、Embedding、重排及其他咨询处理组件；API 模式须在知晓服务商及内容范围后开启。原文可能包含个人信息，官方公开也不能默认无差别再发布；优先最少必要信息，避免索引泄漏身份。

案例资料按四层分别核查，不把项目政策写成法律禁令：

1. 法律限制/禁止：不公开审理、未成年人、国家秘密、商业秘密、个人隐私等；
2. 官方公开状态：裁判文书是否上网、案例是否发布、是否已隐名；
3. 再利用许可：来源服务条款、著作权/数据库权利、是否允许训练与再分发；
4. 项目采集政策：可在核查前保守不收某类案件，但必须标注为项目政策，不能表述为法律禁令。

“不公开审理”不等于该案所有资料一律不能用；官方公开也不等于可以无限再发布。案例原文、索引与微调数据不进入开源仓库；只提供目录与允许的导入方法。索引发布前评估是否可还原原文。训练/出境按同一矩阵处理；真实咨询不默认进入训练集。

文本与案例均是不可信输入，不执行其中指令。代码、数据、模型许可证分别核查，未明确可再分发的材料不打包进开源仓库，必要时仅提供目录与允许的导入方法。测试数据优先使用明确标记的虚构案情。
