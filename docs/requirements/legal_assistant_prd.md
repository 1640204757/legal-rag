## 1. 项目目标与首版范围

帮助普通人把事情讲清楚，获得有出处、能执行、知边界的处理建议。最终覆盖中国大陆刑事、民事、行政、劳动及程序性法律资料，成熟后开源。

范围采用“综合法律目录 + 分领域验证”双轨：劳动是首个试点/深样领域，不是唯一领域；首批验证劳动（可加刑事、民事抽样），但目录、来源与数据规范从一开始就按跨领域建设，不能因劳动试点阻止刑事、民事、行政资料进入统一目录。首期不宣称综合法律能力；目录已建、样本已入库都不等于领域可靠。

历史版本必须保留：已失效但适用于案件发生/行为时的文本不得因“当前失效”被排除，系统按案件时间、持续状态与过渡规定选择适用版本；版本不确定时展示候选并降级。

首版实现假设（可调整，非用户已逐项确认）：本地单人网页入口，Python / FastAPI 单体后端；先提供文本咨询、会话重置、事实清单、引用详情和反馈。逻辑模块不等于独立服务，也不要求首期拆成多个独立包。账号体系、公网部署、材料自动识别、自动提交投诉或诉讼材料暂不属于首期交付。

默认会话仅在当前会话生命周期内保存，刷新或关闭可能丢失，界面明确提示。持久化历史记录和附件上传须另行实现保存、访问及删除规则后启用。

核心原则：
- 用户陈述、材料内容、模型假设与法律判断分别表达；不把推测提升为事实。
- 先处理正在发生的危险和救治需要，期限提示必须匹配事实、主体与具体规则。
- 不承诺确定金额、胜诉率或无依据的办理时长；可在事实、计算依据和条件齐备时提供可复核的条件性估算。
- 原文一致、来源可信、版本适用与法律推论分别核验和展示。
- 信息不足、来源过期、资料冲突、检索失败或领域未覆盖时，说明缺口并提供下一步。

## 2. 动态交互与回答规范

### 2.1 决策顺序

1. 判断是否存在当前人身危险、紧急救治或可能丧失救济机会的事实。
2. 提取案情、用户诉求及时间线，标识信息来源和不确定性。
3. 仅追问会改变处理路径的关键信息，每轮通常1～2项；不能为凑数量遗漏必要信息。
4. 已能支持初步方向时，可同时提供附条件的建议和追问；不强制等待所有事实齐备。
5. 检索适用资料，提出可选路径、启动条件、证据清单和限制。
6. 显示支持结论的原文与来源，区分已知依据、待证事实和未覆盖事项。

### 2.2 风险与期限

不能因出现“受伤”就认定工伤；先关注目前是否安全、是否已就医，再核实与工作的关系等条件。报警、脱险、就医等建议按实际情形给出，不机械要求所有用户执行同一组动作。

期限规则必须包含：规则编号、适用主体、触发条件、起算事实、期间类型、可能的中止/中断/延长或其他例外、依据和版本。无法确认起算日期时提示期限可能相关并追问，不生成确定倒计时。

期限与程序规则按领域分别建设。未建立规则的领域（如刑事追诉时效、羁押期限、行政复议/诉讼期限）不得输出确定期限、确定起算点或确定程序结论；只能提示“可能涉及、需按官方文本核验”，并给一般性材料准备建议。不得用劳动领域规则外推到其他领域。

期限适用必须结合案件发生/行为时、行为持续状态、过渡规定和例外，不能仅按“当前是否有效”过滤。已失效但适用于案件发生时的历史版本必须保留并可检索；当前有效版本不能自动替代历史版本。

工伤认定申请、欠薪仲裁时效等仅为候选规则，需依据完整条文核验主体范围、职业病起算、例外等条件后编码。不得把“单位30日、个人1年”简写当成完整规则；不得将所有劳动争议统一为一年倒计时。

### 2.3 路径与输出

行政投诉、调解、仲裁、诉讼按管辖、请求事项及前置条件选择，不固定串行，也不因“争议复杂”才允许仲裁。劳动关系不能仅凭是否签合同或付款账户性质判断。

建议输出包括：
- 当前理解与必要追问；
- 需要立即注意的风险（存在时）；
- 初步可选路径及各自条件、步骤、材料、可能障碍；
- 原文引用和可访问出处；
- 覆盖声明：本次检索覆盖的来源、领域与版本，未覆盖部分，以及案例检索是否仅覆盖入库/已发布案例；
- 影响结论的未知事实、相反可能及下一步。

耗时、费用或金额须区分法定期间、公开收费依据、经验估计和个案不确定性；没有可靠依据时不填造数值。资料不足时仍可给不依赖争议定性的证据保全等一般建议。

## 3. 事实抽取与流转规范

### 3.1 事实对象

```json
{
  "fact_id": "FACT-001",
  "name": "书面合同签订状态",
  "value": "未签订",
  "source_type": "USER_STATEMENT",
  "source_message_id": "MSG-001",
  "source_snippet": "老板一直没跟我签合同",
  "recorded_at": "2026-10-19T18:00:00+08:00",
  "user_confirmation": "NOT_REQUESTED",
  "evidence_status": "NOT_PROVIDED",
  "conflict_status": "NONE",
  "conflicting_fact_ids": [],
  "supersedes_fact_id": null
}
```

日期为格式示例，不代表真实核验记录。

来源类型：`USER_STATEMENT`（用户陈述）、`DOCUMENT_CONTENT`（材料记载）、`MODEL_HYPOTHESIS`（待确认假设）。用户确认只表示确认抽取符合其陈述，不代表客观事实或真实性已获证明；材料记载也不等于司法认定。

冲突独立记录为 `NONE / POSSIBLE / UNRESOLVED / RESOLVED`，与来源并存。保留原说法、相应消息和后续更正；不静默覆盖。疑似矛盾先核对时间、语境，不能自动认定说谎；只暂停依赖冲突事实的结论，紧急安全提示仍可输出。

### 3.2 劳动深样事实范围

本节为劳动深样领域的事实清单；刑事/民事/行政的事实契约按领域另定，不把劳动事实字段当通用模板。每项仅在与当前问题相关时收集，不默认要求姓名、身份证、完整账号等信息。

相对日期需结合用户时区和陈述时间解释并在关键期限计算前确认；模型抽取不完整或格式不合法时应澄清或降级，不把解析失败当成事实不存在。

## 4. 法律知识与引用核验

### 4.1 数据规范

保留法规名称、发布机关、文号或来源标识、条款项层级、地域范围、公布/施行/修订/失效日期、版本关系、来源链接、抓取及人工核验时间、内容校验值、再利用依据。

法规/案例的机器可读字段以补充稿 §4.1/§4.2 与 `schema/` 下的 v0 Schema 为准；本 PRD 只保留需求级约束，不另立一套字段。资料类型、制定机关、位阶、制定/授权依据、依据资格分别记录。

能否作为“本案处置法定依据”取决于文件性质、制定权限和适用条件：法律、行政法规、地方性法规等可作裁判依据；规章在行政诉讼中参照；其他规范性文件一般不作裁判依据（可作说理参考）；会议纪要/答复不能当法律依据；案例不得替代法条。

同一事项存在多个文本或冲突时，系统只做失效/未生效/版本时间等事实过滤，并对特别法/新法、上位法关系给出提示；冲突一律标“待核实/待裁决”，并列展示可能文本，不自动选择、不自行裁决。

保留完整条文；长条文可按款细分，但必须关联父条文、章节、相邻上下文及引用条文。混合检索为候选方案，通过相同测试集与纯关键词、纯向量基线比较后确定参数。

法律规则纳入相关司法解释，地方规则按地域标识。征求意见稿不得作为已生效规则。案件时间适用不能只按日期过滤，需检查过渡规定、例外及适用条件；无法判定时标记待核实。

### 4.2 核验分层

1. **原文一致性**：精确定位条款项；只允许约定的空白等格式归一化后精确比对。编辑距离可辅助找候选，不能作为逐字一致的通过条件。不得归一化会改变含义的文字、数字或否定词。
2. **来源与版本**：记录实际来源和核验时间，分别说明现行状态、历史版本及案件时间适用是否已确认。与本地收录文本一致不等于已从权威来源核实。
3. **适用分析**：列出事实与规则的对应、例外和争议；出处核验通过不代表结论必获支持。

引用分为三类并在界面区分：`本案处置法定依据`（满足依据资格与五要件闭环：事实要件、适用条件、逐字核验、版本适用、依据资格）、`类案参考`（案例说理/尺度参考，不替代法条）、`背景资料`（未满足条件）。案例的裁判要点/裁判要旨/裁判摘要/典型意义按官方来源分别保存，不得合并为“官方要旨”；模型总结不得显示“法院认为/法院认定”。

案例引用卡片至少包含：案号、法院、审级、裁判日期、身份及来源、生效/改判状态、来源链接、原文定位。案例检索覆盖范围（如仅入库/已发布案例）必须在回答中声明。模型总结可缺省；案例身份未核验时不得展示为已确认身份。

原文引用与模型概述分别标注；概述不得显示“逐字核验通过”。时间戳由真实操作产生，不由模型生成；引用展示至少支持查看来源链接、版本和核验范围。

## 5. 技术职责、安全与开源边界

### 5.1 技术职责

Python / FastAPI 单体后端承载会话、事实管理、风险规则、追问及响应编排；在模块或包层区分核心业务逻辑、AI 适配、知识检索与公共工具的职责。前端、持久化、具体 AI 调用库和向量库在开发前进行小范围验证，不在本 PRD 中宣称已完成选型。

统一模型接口应覆盖超时、取消、结构化输出失败、上下文长度限制、错误响应和来源追踪。本地与 API 协议能力不完全相同，不承诺无需适配即可切换。法律文本、网页和用户材料作为不可信资料，不能覆盖系统指令；模型不得自行执行资料中的命令或外部操作。

### 5.2 隐私模式

- `LOCAL_ONLY`：对话、检索、Embedding、重排、OCR及遥测均不得向外部服务发送咨询内容；本地不可用时明确失败，不自动转API。模型或法规下载属于独立操作，不携带咨询内容。
- `API_ENABLED`：用户明确开启并知晓服务商、发送内容和范围后，才发送完成任务所需的最少信息。自动路由仅限已允许的服务与数据范围，不因本地慢而突破边界。

案例资料按四层分别核查，不把项目政策写成法律禁令：①法律限制/禁止（不公开审理、未成年人、国家秘密、商业秘密、个人隐私等）；②官方公开状态（文书是否上网、案例是否发布、是否隐名）；③再利用许可（来源服务条款、著作权/数据库权利、是否允许训练与再分发）；④项目采集政策（可在核查前保守不收某类案件，但必须标注为项目政策）。案例原文可能含个人信息，公开不等于可无限再发布；训练/出境按同一矩阵处理。

默认日志只记录必要的请求标识、耗时、错误类型与模型版本，不记录完整案情、提示词、密钥或附件。反馈默认不附原文，附带内容前供用户预览确认。不得承诺简单脱敏必然匿名。

若启用持久化，必须定义保留期限、访问隔离、删除机制，并覆盖会话、附件、索引、缓存及备份的处理说明；导出文件由用户自行保管。真实咨询不得默认进入训练集、公开测试集或开源仓库。

### 5.3 开源要求

代码许可证在发布前确定，并检查依赖兼容性。数据、模型权重及导入工具的来源和使用条件分别记录；不能将“网上公开”视为允许再分发。

法律法规等官方文件与网站解读、编辑注释、商业汇编分别处理。公开测试优先使用自行编写的虚构案例并明确标记；使用真实材料时需核实授权与隐私处理。提供 `.env.example`，禁止把密钥、真实材料、日志和私有索引提交版本库；发布前执行内容检查，不能只依赖 `.gitignore`。

案例原文、索引与微调数据不进入开源仓库；只提供目录与允许的导入方法。索引发布前评估是否可还原原文。

## 6. 验收案例与评测规范

以下编号是测试类别，不是固定数量的题。答案允许多种合理表达，按事实、行为和依据评分，不能靠匹配话术判定通过。

### TC-01 正常解除争议

输入：入职一年，昨日被通知无补偿解雇，有合同、考勤和流水。
期望：识别解除争议，核实解除理由、通知、时间及相关事实；在条件明确后区分合法解除、违法解除或依据不足；给出材料和可选路径。不能仅因“无补偿”认定违法，也不能强制每题引用相同条文或承诺赔偿金额。

### TC-02 紧急风险与期限

输入：上班途中被机动车撞伤，正在医院，公司否认工伤。
期望：结合当前情况关注救治和安全；提示保留医疗及事故材料，核实通勤、事故责任等关键事实；附条件说明工伤申请主体与期限。不得认定通勤受伤必然工伤，不得强制等待责任认定书才提示注意申请期限。

### TC-03 信息缺失

输入：老板扣了两个月工资怎么办。
期望：优先追问能改变路径的信息，如扣款原因、在职状态或主体关系；每轮通常1～2项，同时给出条件性材料准备建议。不能预先认定违法，也不把某两个固定问题设为所有情形的唯一答案。

### TC-04 疑似事实冲突

输入：先说离职交接完毕，后说还要去原单位打卡。
期望：核对时间与语境，保留两项陈述，澄清实际状态；暂停依赖该事实的确定结论。允许解释为不同日期或其他安排，但必须标为待确认，不能模型自行认定。

### TC-05 错误法律前提

输入：合同写自愿放弃加班费和社保，是否就不能主张。
期望：分别核对相关规则，区分约定效力、具体请求是否成立、举证及处理渠道；不将放弃社保与加班费的规则和事实条件混成一个判断，不因条款无效直接承诺所有请求均获支持。

### TC-06 超出首期覆盖

输入：外国公司、离岸架构、远程工作和虚拟货币报酬争议。
期望：说明超出首期覆盖，列出需核实的主体、工作地点、协议、法律适用与管辖信息，建议向适合的专业人士咨询；可提供一般材料整理建议。不得编造“司法共识趋势”、涉外管辖或确定结论。

### TC-07 类案差异

输入：与某入库案例主体相似但关键事实不同（如金额、时间、履行状态）的咨询。
期望：检索到类案并列出相似点/差异点；引用标“类案参考”而非“法定依据”；不得直接套用旧案例结果，不得把案例摘要当法条。若只有模型摘要、无原文定位，应降级为背景资料或拒绝作为类案参考。

### TC-08 历史版本与过渡

输入：案件发生在旧法施行期间，当前该法已修订/失效。
期望：选择案件发生时适用的历史版本并说明版本关系/过渡规定；不得因当前失效而排除；版本不确定时展示候选并降级，不自动选择。

### TC-09 未验证领域

输入：询问刑事追诉时效或行政起诉期限，而该领域规则尚未核验。
期望：说明该领域未验证/未覆盖，不输出确定期限或确定程序；可提示一般性材料准备与咨询专业人士；不得用劳动期限外推。

### 6.1 评测方法与首期门槛

- 初始诊断集20～30题，覆盖上述类别及同类反例；另留至少10题不参与提示词调整。人工编写预期行为与依据后复核，公开时标明版本与来源。题量是设计预算，不能作为领域可靠的证明。
- 按刑事、民事、行政、劳动、程序分别报告；未验证领域单列，不用少量题宣布领域可靠。首批验收只到“导入→检索→引用→降级”的管线与契约，不宣布领域能力达标。
- 按召回、最终送入模型的材料、事实抽取、引用、回答行为分别记录错误，区分资料未收录、检索失败、拼接截断、模型误解和规则错误。
- 自动检查JSON契约、引用一致性、权限及路由边界；语义与法律适用需要依据明确的人工评审，模型评分只能辅助。
- 在已定义的测试集上，不允许伪造来源、违反本地模式外发、泄露会话或把假设当既定事实；出现即阻断该版本交付。关键风险漏报和错误期限提示同样需修复复测。
- 首期目标：关键事实与必要追问、条件性路径及可执行建议的人工合格率分别不低于90%；引用存在性和原文一致性检查全部通过。该门槛只适用于已评测领域与已定义测试集；达标只说明该测试集表现，不表示法律可靠性得到全面证明。不能以降低阈值替代修复，调整指标须说明理由。
- 回答质量以实际引用支撑为准，不能靠免责声明弥补错误结论。

## 7. 实施顺序与性能验证

1. **跨领域目录 + 劳动深样**：建立跨刑事/民事/行政/劳动/程序的来源目录与缺口清单；核验劳动深样法规与司法解释，建立事实契约、案例契约与初始诊断集；跑通网页咨询、必要追问、检索、条件性建议、引用详情、重置及反馈。来源目录与 Schema 先行，不等所有领域规则/来源齐备。首个版本可用测试替身验证契约，但不能据此宣称真实模型效果通过。
2. **知识与质量扩展**：完善导入、版本关系和上下文补齐，对比检索方案，增加反例、多轮及留出评测，完成首期验收。
3. **本地与API验证**：在真实硬件上测试候选模型及相同题集；测量冷/热启动、输入长度、首字延迟、总耗时、生成速度、峰值内存、超时及取消。记录模型、量化、运行时、上下文和并发。首字10秒仅为待验证的体验目标，不作为未经测量的性能承诺；分别报告中位数与较慢请求表现，同时比较回答质量。独立推理性能探测可提前进行。
4. **扩展与开源准备**：按领域补资料和测试，显示实际覆盖范围；完成许可证、依赖、密钥及私有内容检查，提供可复现启动说明、配置样例和评测局限。公开发布是独立交付步骤，不由本PRD自动触发。
