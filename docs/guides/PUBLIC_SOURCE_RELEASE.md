## 向量数据库到底怎么处理

重建链路是：**原始资料与解析结果 → 同一嵌入模型生成向量 → 向量缓存 → Qdrant 集合**。

`data/local_index/` 是可复用向量缓存；Docker 中的 Qdrant 是数据库；`data/models/`、`data/ollama_models/` 是模型。三者各占一份空间，不能混为一谈。

源码仓库不保存 Qdrant 数据目录。使用者准备自己的 Qdrant 和模型，核对资料后通过网页“加载新资料并入库”或项目解释器运行 `python -m local_rag.index` 建库。重建需消耗时间、算力及磁盘；模型身份或维数改变不能混用旧向量。详见 [数据库与更新流程](QDRANT_KNOWLEDGE_PIPELINE.md)。

若要保留现有入库成果，可按 [Qdrant 官方快照说明](https://qdrant.tech/documentation/operations/snapshots/)对本项目集合制作并下载快照，再在兼容实例中做恢复验证。快照可能包含条文及元数据，也要按资料发布边界处理，不能直接公开。仅服务器上创建快照而未下载、校验、恢复，不算已经完成异机备份。

当前维护者的 Qdrant 可能还存其他项目集合。不要删除容器、整个卷、Docker 虚拟磁盘或执行 `docker system prune --volumes` 来给本项目腾空间。Docker 未启动时无法核实实际集合、挂载和存储大小；此时保留数据库。

## uv 与本项目的关系

本项目尚未迁移为 uv 项目；本机 uv 的共享下载缓存与本项目虚拟环境是不同目录。`uv cache dir` 可查看实际缓存路径，`uv python dir` 查看受管理 Python 路径。Python 安装本体不是缓存，其他项目可能正在依赖它。

按 [uv 官方缓存说明](https://docs.astral.sh/uv/concepts/cache/)使用 `uv cache prune` 清除无用缓存，或 `uv cache clean` 清空缓存。清理后未来安装可能需要重新联网下载。不要直接手删缓存内部文件；不删除共享 Python 或 uv 工具环境。本轮对共享 uv 目录先做只读检查，未把“检查占用”当作删除所有共享环境的授权。

**后续授权与执行**：用户明确选择清空共享缓存后，已执行官方 `uv cache clean`，工具报告移除164,969个文件、约 **10.9 GiB**。实测文件逻辑总量约10.86 GiB；共享 Python 本体约60 MiB并予以保留。uv 与项目清理合计观察到D盘可用空间增加约 **12.4 GiB**，该变化也可能受其他程序同期写入影响。
