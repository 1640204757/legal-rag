- 第一层仍按3600个条文正文字符整条选择；第二层按 `sum(UTF-8内容字节+每条消息32字节预留)`、6800字节目标线整条装材料，最终7000字节硬顶。系统提示、问题、材料元信息、覆盖缺口与历史均通过真实组装计入。
- 默认是新会话，历史为空，此时装配路径与改造前逐字节一致（见 `test_single_turn_query_and_messages_are_byte_identical`）；不代表任意多轮历史下都能送同样数量。`--history-file` 可注入最多五轮合法历史：有历史时先给最近一轮留 700 字节余量再装历史，超长输入按“丢历史 → 截断问题副本 → 材料回吐到一条”降级，不再在 chat 前报错；报告里的 `history_bytes` 只统计真正送进模型的历史视图（装配会把旧回答压成一行）。
- 官方切片只读复用已有校验缓存/已验收暂存，禁止新建网络采集客户端，不写库或改缓存。缓存缺失时保留真实目录缺口提示。真实回答基线使用评测器原有官方抓取策略；不能把只读统计当作每次联网补充均不变的保证。
- 实际送模条文从真实输入恢复并核对完整正文；目标标签只用于事后计分，不进入检索或消息。holdout仅落汇总，明细只含dev/v2。
- 丢弃比例分母为实际返回的本地候选及官方补充总数，分别记录字符预算和字节预算的丢弃；不把未返回的候选计作预算丢弃。

## 已决定：保留4条，不修改生产送模请求

**是什么原因。** 正文只有约360–420字符时就可能用满消息字节预算，因为系统提示固定占3320字节，条文法名、来源等元信息及缺口提示也占空间；额外请求的条文大多仍被整条排除。6条方案还出现原有正确材料送模丢失。

**怎么认出来。** 同一冻结题集、同一生产组装逻辑下，5条只把全部156题的目标送模从86增到87；holdout/v2没有净增。6条总体回到86，并丢失D0501。没有把“模型候选增加”直接记成“正确材料已送入”。

**怎么改。** 按用户明确选择保留原生产代码：`_run()`主检索仍用默认前4，`Retriever.search()`默认4、每路池20和各排序规则均未改；展示仍为前8加尾部。`test_display_candidates.py` 的 `retriever.calls == [4, 8]` 及送模标记断言继续保留，只有真正采用5/6才需变更这些断言。本轮保留的是预算测量工具、评测器透传修复、逐题计时和回归测试，不声称回答质量已提升。没有候选回答报告，因而没有5条与4条的拦截/错引增减结论。
