### 第 2 层也会影响检索，共三处

第 3 层负责**主排序**，但第 2 层在材料组装时还会追加官方目录补充条目、并按预算整条截断，
所以它不是唯一影响**检索结果**的地方：追加在 `service.py:619`（`hits = list(hits) + supplements`），
按 3600 字预算整条取舍在 `:622-629`，再按 UTF-8 字节预算整条装材料在 `:660-733`；
**这三处都不重排**，原有顺序保持不变。`service.py:597-614` 另有三处影响检索输入：

| 影响 | 代码 | 说明 |
| --- | --- | --- |
| a) 历史拼到问句前面 | `service.py:598-599` | 取用户历史发言最后 800 字，拼在本次问句前面，所以 3.3 的“原话”在多轮时其实是“历史 + 本句” |
| b) 领域不覆盖时直接跳过检索 | `service.py:600-605` | 问句含“刑事”“行政诉讼”等词、库里又没有对应领域时标 `out_of_scope`，`hits` 直接为空，不调 `search` |
| c) 地域规则缺失时清空候选 | `service.py:353-373`（`uncovered_foreign_region`）、`:607-611` | 判定为境外/地方细则缺失时 `hits = []`，前面拿到的候选全部作废 |

另外，页面“更多候选”和材料预算也都用第 2 层拼好的同一个 `query`（`:614`、`:629-632`），
所以这三处影响会一路传到展示和送模。

### 第 2 层的提示词装配顺序（2026-11-07 起）

送模消息固定按“系统提示 → 历史视图 → 本轮材料包”组装，字节口径是
`sum(UTF-8 内容字节 + 每条 32 字节)`：

1. **材料第一顺位**：先按原 3600 字规则和 6800 字节整条装候选材料；历史为空时这条路径与改造前逐字节一致。
2. **历史按余量倒序填补**：有历史时先给最近一轮留 700 字节，再从最新一条往前整条装；装不下就停。
   助手旧回答在装配时压成一行正文，用户发言保留开头 400 字节；`Session.history` 本身仍存全文。
3. **双侧保底**：余量放不下最近一轮时，从名次最低的材料回吐，但至少保留一条完整材料。
4. **硬顶兜底**：超过 7000 字节依次丢历史、材料回吐到一条、截断送模问题副本（检索与金额/期限豁免仍用完整问题）；
   全过程不外抛超长异常。落地与验收记录见 [LOCAL_RAG_README.md](LOCAL_RAG_README.md)。

### 第 2 层会话底座：冷存储与定向回查（2026-11-07 第 2 步）

第 1 步只解决“不崩”，第 2 步补两件事：**会话不再只活在内存里**，以及**远期用户原话能定向找回**。

#### 1. 本地 JSONL 冷归档（`local_rag/session_memory.py`）

- **位置与格式**：每个会话一个 `data/sessions/{sid}.jsonl`，一行一个事件；目录已进 `.gitignore`。
  用户事件含 `role/content/round/index/timestamp`；回答事件含 `role/raw_answer/answer/blocked/
  blocking_issues/materials_sent/status/round/index/timestamp`。被拦截、超时、出错也照记，方便事后核对。
- **写入**：`append_event()` 用 `asyncio.to_thread` 跑同步追加，写完 `flush + fsync`，不阻塞事件循环。
  `start()` 先把用户提问排入归档线程，同时立刻开始检索/生成；写回答前再等用户条落完，保证文件顺序。
- **容错**：`read_events()` 逐行 `json.loads`，末尾半截行或任何损坏行直接跳过，不会让整份档案失效。
- **删除**：`delete_session_archive(sid)`（服务层包装 `ChatService.delete_archive`）支持用户主动清空；
  没有文件时返回 `False`，不报错。会话编号经过白名单校验，拒绝路径穿越。
- **兜底**：归档失败绝不阻断问答；`ChatService(session_dir=False)` 可关闭归档（测量脚本用它保持只读）。

#### 2. 只在用户原话上做 BM25 回查

`recall()` 的输入是 `read_user_turns()` 或 `turns_from_history()`，**索引里只有 user 消息**，
助手的推测、格式套话和旧回答永远不会被当成用户事实。

触发条件分两档：

1. **明显指代**：`前面说的 / 之前提的 / 一开始 / 上次说 / 借条 / 第X轮` 等（`REFERENCE_CUES`）；
2. **没有指代但高度相关**：问句与某条早期原话至少共享 6 个双字词项，且重合度 ≥ 50%。

有指代但 BM25 一分未得（例如“前面说的那个怎么办”），说明指代严重模糊——**不注入**，
留给模型在 `## 追问` 里向用户澄清。当前轮与最近一轮不在候选里（最近一轮已由历史视图承担）。

命中后最多注入 2 条，整行格式固定为：

```text
【前情陈述（第N轮用户原话）】：“……”
```

单片（含前缀和引号）≤ 200 字节、合计 ≤ 500 字节，超长按 UTF-8 字节截断并补“……”；
片段放在本轮用户消息的 `RagInput.recalled` 受控区（【已知事实】之后），**不进 system**。
`recalled` 为空时 `render_user_prompt()` 与改造前逐字节一致，单轮钉扎不受影响。

#### 3. 校验器不再误杀“旧事实”

原实现只把**本轮 question** 当作复述豁免：

```python
duration_issues = deadline_grounding_issues(checked_answer, material_rows, question=question)
amount_issues = amount_grounding_issues(checked_answer, material_rows, question=question)
```

用户第 1 轮说“借了 5 万元”，第 5 轮模型如实回答“5 万元”时，本轮 question 没有这几个字，
就被判成捏造数据而整轮拦截。现在改为：

```python
context_question = question + " " + recalled_user_text   # 仅当轮实际注入的回查片段
duration_issues = deadline_grounding_issues(..., question=context_question)
amount_issues = amount_grounding_issues(..., question=context_question)
```

`answer_scenario_issues` 仍只看本轮 `question`，检索问句也不因回查改变；回查为空时
`context_question == question`，行为与改造前完全一致。

**验证。** `tests_local/test_session_memory.py`（8 条）覆盖写入、半截行、删除、5 轮回查、
助手隔离、指代模糊不注入、单片/合计字节上限；`tests_local/test_dialogue_recall.py`（7 条）覆盖
5 轮注入到用户消息、助手回答不进回查源、金额/期限误杀的前后对照、服务层确实把回查文本传给两个校验器、
单轮上下文不变。全量测试 1136 通过、14 跳过。

**已知边界。**

- 回查只解决“旧事实被预算裁掉/被校验器误杀”，**不证明多轮回答更准**；仍缺多轮会话评测集。
- 回查只看词面（双字 BM25），同义改写、跨轮推理和“他/那个”这类无词面线索找不到。
- 最近一轮默认不进回查候选；如果它恰好被历史预算裁掉，本轮不会补回，需要下一轮指代或追问。
- 归档是本地明文，删除接口只删对应会话文件；不做加密、不做跨设备同步。
- 服务重启后内存会话仍会丢；归档已落盘，但页面还没有“从档案恢复会话”的入口。

## 三、怎么定位该改哪一步

顺序不能颠倒：**先跑全量归类，再看单题细节。** 不许拿一道题当理由改全局参数。

### （一）跑全量归类

```powershell
$projectPython = (Get-Content .local-python-path.txt -Raw).Trim()
& $projectPython -B -X utf8 scripts/measure_retrieval.py --split dev
```

`--split dev` 实际跑的是 **80 道 dev + 36 道 v2**（`scripts/measure_retrieval.py:225-226`），
下面只取 dev 那一段。本次运行结果：dev 前 4 命中 51、前 8 命中 61、前 8 + 页面尾部 73。

### （二）归类表：代码分五类，“池内/池外”是附加标志

注意别把文档写成代码里没有的枚举。`CATEGORIES` 一共五个值（`retrieval_measure.py:20`）：
`命中 / 被0.38挡掉 / 排不上 / 找不到 / 出错`。**“池内/池外”不是第六类**，
它是“排不上”底下再分的 `outside_pool` 标志（`retrieval_measure.py:86`）：

```python
record["outside_pool"] = record["diagnosis"] == "排不上" and record["pool_rank"] is None
```

| 归类 | 判定条件（`retrieval_measure.py`） | dev 题数 | 该动哪一步 |
| --- | --- | --- | --- |
| 命中 | `top4_rank` 有值（`:55`） | 51 | 不动 |
| 被 0.38 挡掉 | 融合前 60 里没有、语义前 20、分数 < 0.38（`:58-60`） | 0 | **3.3** 阈值 |
| 排不上·池内 | 归类为排不上（`:62`）且 `pool_rank` 有值 | 15 | **3.4** 融合 |
| 排不上·池外 | 同上，且 `outside_pool=True`（`:86`） | 7 | **3.2 / 3.3** 召回深度 |
| 找不到 | `bm25_rank`、`dense_rank` 都为空（`:64`） | 7 | **3.1** 词表 / 概念缺失 |
| 出错 | `error` 有值（`:53`） | 0 | 先修故障 |

合计 51 + 0 + 15 + 7 + 7 + 0 = 80。**“排不上”总数 22 = 池内 15 + 池外 7。**

**“池”指哪个池，要说清**：池 = 生产两路各前 20 合并后的**完整融合排序**
（`retrieval.py:20` `CANDIDATE_LIMIT`、`:656-663` 取两路前 20、`:674` 起做融合），
`search(top_k=60)` 只是把这份排序不截断地取出来（`scripts/measure_retrieval.py:105`）。
本次 dev 的 `pool_rank` 最大只到 37（`details.json`），所以 60 的深度对现有题目是够的：

- **池内** = 正确条文在这份融合排序里出现过，但没进前 4；
- **池外** = 融合排序里没有它，只有 3.2 或 3.3 某一路的前 60 里有。

这正好对应两条不同的修法：池内是排序没排好（3.4），池外是合成时根本没进来（3.2/3.3）。

两个容易读错的点：

- **池外 7 题不是“完全看不到”。** 它们在某一路上第 21–60 名出现过，页面的“更多候选”能列出
  （`retrieval.py:790` `tail_candidates`，`TAIL_DEPTH=60` 见 `:22`），所以“前 8 + 尾部”是 73/80。
  真正完全看不到的只有那 7 道“找不到”。
- **被 0.38 挡掉这次是 0 题。** 不代表阈值永远没问题，只代表本批 dev 没有这种失败。

### （三）单题归因，按归类走，不按感觉走

拿到某题后，按下表对号入座；**3.1 是否命中只作参考，不作为先改哪一步的依据**：

| 归类 | 先做什么 | 再考虑 |
| --- | --- | --- |
| 命中 | 不动 | — |
| 被 0.38 挡掉 | 看该题语义分数离 0.38 差多少（`trace_layers.py` 会打印） | 3.3 阈值（风险最高，一次只改一处） |
| 排不上·池内 | 看 3.4 里是哪条权重把它压下去 | 3.1 能否把它直接顶进前 4 |
| 排不上·池外 | **只能改 3.2/3.3 的召回深度或覆盖** | 3.1 补概念 |

### （四）两条防错规则

1. **先归类，再决定改哪一步；词表命中与否只是参考。**
   上一版写的“词表没命中就不许调排序”会和 D0203 这种“池内排不上”打架：
   它既没命中词表，又确实属于池内排不上。按归类走，答案是 3.4，不是拿词表去否定归类。
2. **“池外”的排不上不许用调融合权重来处理。**
   池外的定义就是“根本不在合并池里”，3.4 只在池内排序，调权重对它没有任何作用，
   只会把别的题弄坏。要改只能改 3.2/3.3 的召回深度或 3.1 的覆盖。

## 四、新增词条（3.1）的准入规则

词表是最容易“越加越乱”的地方，按三条走：

1. **一条词条对应一个法律概念，不许照抄某道题的原句。**
   例如“租赁物正常损耗”“行政诉讼起诉期限”可以；把 D0203 的整句口语抄进词表不行——
   那等于为一道题写死，换个人换个说法就失效。
2. **每次新增都要报 alias 统计：触发 / 变好 / 变差 / 不变。**
   这三个数的口径是“同一批题里，扩展后的 BM25 名次相对原话名次”的变化
   （`retrieval_measure.py:104-108`：`better` / `worse` / `same`，第 60 名以外按 61 计，见 `:98-99`）。
   **变差 > 0 必须逐题说明原因**，不能说“总体更好”就带过。
3. **只能根据 dev 补词条，holdout 只看汇总。**
   `DETAIL_SPLITS` 只允许 dev 和 v2 出逐题明细（`retrieval_measure.py:19`），
   holdout 一旦被用来挑词条就失去盲测意义。

本次运行的实际 alias 统计（dev）：触发 24 题，**帮忙 21 / 帮倒忙 1 / 没影响 2**。
唯一变差的是 **D0710**“离婚后九岁的孩子非要跟爸爸”：
词表触发后 BM25 从第 1 掉到第 51，但语义路（3.3）排第 3 把它捞进池，最终仍在前 4。
**这说明“alias 变差”不等于“题目答错”，必须同时看前 4 结果**——这也是第五节要把两项记录一起报的原因。
