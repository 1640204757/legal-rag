# 展示候选：前8条加"更多候选"

## 为什么要改

第0步的实测（[检索诊断尺子](RETRIEVAL_MEASUREMENT.md)）显示，很多正确条文其实找到了，只是没排进前4：

- 开发题前4命中 32/80，前8命中 44/80；
- 关键词、语义两路各自前60名里没进前8的条文也展示出来，前8加尾部能覆盖 60/80。

原来页面"检索候选"里显示的是 `retrieved`，也就是送进模型、又通过了预算筛选的那几条（[service.py](../../local_rag/service.py) 的 `materials`），所以找到了也看不到。这一步把"给你看的"和"送给模型的"分开。

## 状态

- 后续默认回答已接入 [材料阅读许可](MATERIAL_READING.md)：越权或来源无法完整核对时整段拦截、清空引用卡片，但页面检索候选原文仍可查看；展示前8/尾部与原送模数量规则均未修改。
- 新许可Web单次复验：34.23秒完成、无个人判责/金额结论，展示前8、尾部110；数据库和索引ready。仅此一次样本，不取代既有D0803证据或全面回答验收。
- 已确认：本设计（2026-11-02 用户同意，尾部取"两路前60里没进前8的"）。
- 已实现、已验证、待验证的情况以文末"实施记录"为准。
- 2026-11-03后续送模4/5/6条预算试验已完成，用户确认收益不足、保留4条；展示前8与尾部不变，`[4, 8]`调用断言继续有效。详情见 [送模试验记录](PROMPT_MATERIAL_EXPERIMENT.md)。

## 改了什么

1. **检索**：第3步实施时未改 `Retriever.search()`；后续原因1修复只调整查询状态管理，排序与分数不变。新增 `Retriever.tail_candidates(query, exclude_ids, depth=60)`：
   - 关键词：对扩展后的问题做 BM25，取全库前60名（和线上关键词一路相同）；
   - 语义：用原问题的向量查前60名，仍然只要相似度不低于0.38的（和线上语义一路相同）；
   - 去掉 `exclude_ids`（也就是前8条），按它在两路中最好的名次排序；名次相同时语义在前，再按行号；
   - 每条带上 `tail_routes`，记下它在关键词、语义两路各排第几；
   - 语义查询失败时只返回关键词部分，**不改**数据库就绪状态，不会触发"一次失败就一直降级"。
2. **问答流程**：送给模型的材料和原来完全一样（`search()` 默认取4条，预算不变）。另外：
   - 调用 `search(top_k=8)` 得到"前8条"，再调用 `tail_candidates()` 得到"更多候选"；
   - 前8条查询前保存主检索的 `state/error`，在 `finally` 中恢复：内部降级正常返回、成功、外抛异常和取消均不覆盖主检索状态；旧检索器没有状态字段时不要求补齐字段；
   - 放进返回结果的新字段 `display = {top, tail}`，每条标 `sent_to_model`（是否送入模型）和 `material_id`（送入时的编号）；
   - 前8条查询外抛普通异常时，`display` 为空且不影响回答；如果 `search()` 内部降级并返回关键词候选，仍展示这些候选；尾部查询外抛普通异常时保留前8条。取消继续向上传播。地域或领域未覆盖而降级时，`display` 也为空，而且不再多做这两次检索（原有测试 `test_foreign_scope_keeps_real_search_but_removes_domestic_materials` 要求降级的问题只检索一次），和原来清空候选的保护一致；
   - 原字段 `retrieved` 保持不变。
3. **页面**："检索候选"视图有 `display` 时：
   - 先列前8条，标"已送入模型 Mx"或"未送入模型"；
   - 下面一个默认收起的"更多候选（N条，未送入模型）"，每条显示法名、条号、来自哪一路第几名，点开看原文；
   - 旧服务没有 `display` 时，照旧显示 `retrieved`。
4. **测量尺子**：[measure_retrieval.py](../../scripts/measure_retrieval.py) 增加"前8+尾部命中"，调用的是同一个 `tail_candidates()`。

## 怎么验证

- 单元测试：`tail_candidates()` 的取法与失败处理、`ChatService` 的 `display` 字段、页面渲染（用 Node 直接执行 `app.js`）、尺子的新指标。
- 重跑尺子并用 `--compare` 对比第0步快照：线上前4、前8必须一道不变。
- 打开网页实际问一道开发题，看"更多候选"是否显示正确。

## 不做什么与已知限制

- 不改排序、不改送模型的材料、不改预算。
- 每次提问多做2次检索（多算2次问题向量），耗时待实测。
- 原因1已修复：`search()` 单次异常不再改 `store.ready`；下一次语义查询成功自动恢复状态。`ready=False` 的未完成入库边界仍保留，不能通过重试绕过。后续已恢复服务补验，各组前4/前8与11月2日快照变化数均为0。
- 尾部最多约112条（两路各60名去重，再去掉前8），页面默认收起，只显示法名和条号。
- 尾部只是"可能相关"，没有送入模型，也没有经过模型核对。
- 覆盖缺口里那句"部分候选材料因上下文预算未送入模型；右侧仅列出实际提供的材料。"也是送给模型的提示词的一部分。为了不改模型输入，这一步没有改它的文字，所以它和新页面的说法有出入。
