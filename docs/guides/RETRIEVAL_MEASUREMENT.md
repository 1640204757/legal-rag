# 检索诊断尺子：正确条文丢在哪一步

## 这是什么，为什么要有它

现有的 [eval_retrieval.py](../../scripts/eval_retrieval.py) 只看线上前4条有没有命中（[daily_evaluation.py](../../local_rag/daily_evaluation.py) 的 `score_retrieval()` 只取 `hits[:4]`），回答不了"没命中的题，正确条文到底排第几、是哪一步丢的"。

诊断尺子 [measure_retrieval.py](../../scripts/measure_retrieval.py) 专门回答这个问题，给后续每一步修改提供"改前/改后"的对照。两者分工：

- `eval_retrieval.py`：验收尺子，判断改动能不能保留（基线对比、holdout 不退步）。
- `measure_retrieval.py`：诊断尺子，说明问题出在检索的哪一步，并保存线上前4/前8快照，防止误改。

## 状态

- 已确认：本设计（2026-11-02 用户同意）。
- 已实现、已验证、待验证的情况以文末"实施记录"为准。
- 2026-11-03新增独立进程`--without-colloquial`消融：临时关闭整表及依赖锚点，退出/异常原样恢复；不改生产文件或Web。报告`variant`区分`production`和`without_colloquial_table`。最新同模型对照、实际送模与回答失败复现见[根因定位](ROOT_CAUSE_DIAGNOSIS.md)，整表关闭因退步未采用。

## 每道题量哪些数

| 名称 | 怎么量 | 用来判断 |
| --- | --- | --- |
| 关键词排名（原话） | 只用用户原话做 BM25，看正确条文在全库排第几（看到第60名） | 原话本身能不能碰上法条用词 |
| 关键词排名（扩展后） | 加上口语对照表的词再做 BM25，线上实际用的就是这一路 | 和上一个数对比，看对照表帮了忙还是帮倒忙 |
| 语义排名 | 不卡0.38，只读查询语义前60名，并记下正确条文的相似度 | 语义能不能找到，有多少是被0.38挡掉的 |
| 线上前4 | 照原样调用 `Retriever.search(top_k=4)` | 用户现在实际看到的结果 |
| 线上前8 | 照原样调用 `Retriever.search(top_k=8)` | 以后核对"原前八不变" |
| 合并池排名 | 调用 `Retriever.search(top_k=60)`，看合并后的整个候选池（最多约44条） | 进没进合并池、在池里排第几 |
| 前8+尾部 | 页面"检索候选"实际展示的前8条加"更多候选"（调用同一个 `tail_candidates()`，2026-11-02 第3步加入） | 页面能不能展示出正确条文 |

"正确条文"按题目标注的法名和条号判断，和 `score_retrieval()` 的口径相同；一道题有多个可接受条文时，取排名最靠前的那个。

## 每道题归到一类

按下面的顺序判断，先满足哪条就归哪一类：

1. **命中**：线上前4里有正确条文。
2. **被0.38挡掉**：正确条文没进合并池，但语义其实排进了前20、相似度低于0.38，被阈值挡在门外。
3. **排不上**：在合并池里，或在某一路的前60名里，但没排进前4。另记"在合并池外"的数量，也就是只在某一路第21–60名出现，这正是后续"第13–60名尾部候选"想补的部分。
4. **找不到**：两路的前60名里都没有。这是召回结果，不单独证明原因是口语用词；还需检查目标是否在库、问题事实是否足够、标注是否合理，以及语义模型是否遗漏关键关系。
5. **出错**：这道题检索时报错，保留在分母里，不算成功也不算找不到。

归类只说明"丢在检索的哪一步"，不判断条文是否适用于个案。

## 输出与保密规则

每次运行在 `artifacts/local-rag/measure-runs/<时间>/` 下保存三个文件：

- `summary.json`：各组汇总（命中数、前8+尾部命中数、各路前4/8/20/60命中数、各类数量、对照表帮忙/帮倒忙的题数、运行来源）。
- `details.json`：只含 dev 和 v2 的逐题明细。
- `snapshot.json`：每道题只存题号、分组和线上前4/前8返回的条文编号，不含题目原文和标准答案。

保密规则：

- dev（80道）和 v2（36道）：逐题明细可以打印和保存，用于调试。
- holdout（40道）和用 `--file` 指定的外部题集（例如 user10）：只打印、只保存汇总数字，题目、标准答案和逐题排名一律不写进任何文件。
- `--compare 上次运行目录`：对比两次快照；dev 和 v2 列出前4/前8变化的题号，holdout 和外部题集只报变化了几道。
- 任何一道题不是正常的混合检索（`hybrid_qdrant`）或出错，照样出报告，但退出码为2，提醒这不是正常成绩。

## 怎么运行

先启动网页服务（18765）、Qdrant（16333）和 Ollama（11434），并确认索引就绪；连接方式复用 [daily_eval_runtime.py](../../local_rag/daily_eval_runtime.py) 的 `open_runtime()`，只读查询，拒绝写库。

```powershell
$projectPython = (Get-Content .local-python-path.txt -Raw).Trim()
# 日常诊断：80道dev + 36道v2
& $projectPython -B -X utf8 scripts/measure_retrieval.py
# 完整一轮：再加40道holdout（holdout只出汇总）
& $projectPython -B -X utf8 scripts/measure_retrieval.py --split all
# 和上次的快照对比，确认原前四、原前八有没有变
& $projectPython -B -X utf8 scripts/measure_retrieval.py --split all --compare artifacts/local-rag/measure-runs/<上次目录>
# 独立测量进程关闭整张口语表及依赖锚点；不会更改网页配置
& $projectPython -B -X utf8 scripts/measure_retrieval.py --split all --without-colloquial --compare artifacts/local-rag/measure-runs/<生产基线目录>
# 你自己的留出题（例如user10），只出汇总
& $projectPython -B -X utf8 scripts/measure_retrieval.py --file <题目文件路径>
# 查询侧 Instruct 前缀对照实验：baseline / v1 / v2 / v3，措辞写死在脚本里
& $projectPython -B -X utf8 scripts/measure_retrieval.py --split all --query-prefix v1
```

外部题集格式：

```json
{"questions": [{"id": "U01", "query": "口语问题", "expect_any": [{"title": "中华人民共和国劳动合同法", "article_no": "第三十条"}]}]}
```

也接受直接以列表开头的文件，以及 v2 使用的 `expect_hit_articles` 字段名。格式有问题时只提示"第几题缺什么字段"，不回显题目内容。

## 阅读顺序

1. [retrieval_measure.py](../../local_rag/retrieval_measure.py)：纯计算，找排名、归类、汇总、对比快照；不联网、不写盘。
2. [measure_retrieval.py](../../scripts/measure_retrieval.py)：运行编排，连服务、逐题取各路排名、按保密规则写结果。
3. [test_retrieval_measure.py](../../tests_local/test_retrieval_measure.py)：用合成数据和假检索器验证上面两部分。

## 不做什么与已知限制

- 不测"被预算挤掉"：那要复刻整段提示词拼装，放到第2步拆分"展示/送模型"时一起做。
- 不改任何检索逻辑。读取关键词全排名用的是检索器内部的 `_bm25`（只读），因为生产 `search()` 只返回截断后的结果。
- 合并池最多约44条（两路各20条去重，复合问题再补最多4条），所以"合并池排名"最多到44名左右。
- 语义前60名来自不带0.38阈值的只读查询；Qdrant 可能使用近似检索，排名和精确计算可能略有出入（未核实）。
- 标准答案是 AI 草拟、待人工抽检的，尺子的刻度本身可能有错。
